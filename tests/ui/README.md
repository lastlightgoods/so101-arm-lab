# Dashboard UI tests

Automated front-end tests for `dashboard/index.html`, with no framework, npm packages or build step: `stub_server.py` is a threaded Python HTTP server on `127.0.0.1:0` that serves `dashboard/` statically and answers every `/api/*` route from Python objects a test can mutate between steps (`stub.routes[...]`, a route value may also be a callable of the request path, as `/api/locate` is, plus `stub.fail[route] = 500`, `stub.raw[route] = b'{bad'`, `stub.delay[route] = 2.5`; every POST is recorded in `stub.posts`); `apidata.py` builds those objects in the shape `server.py` emits (Jetson online/offline, `emc` present or `None`, datasets with mtimes, record idle / starting / running / paused / reset / done / failed, tegrastats history rows); `driver.js` is a small Node program that opens the page in a fresh tab of a headless Chrome over the DevTools protocol (`/json/new` + the global `WebSocket`, the same pattern as `dashboard/cdp.js`), blocks all external traffic (CDNs and fonts, so the three.js module never runs and nothing depends on the network), hides the self-playing Tempest canvas (whose software-rasterised shadow blur would otherwise keep the renderer's main thread busy and slow every call ~50x), and then takes JSON commands on stdin (`eval` with promises awaited, `key` as real `Input.dispatchKeyEvent` keystrokes, `errors`) while collecting `Runtime.exceptionThrown` and `console.error/warn`; `conftest.py` launches one Chrome per session on a free ephemeral port (never 8765/8766/9333, where the live kiosk runs), one stub and one tab per test, waits for the page's own first poll cycle, then freezes the page's `setInterval` loops so each test drives `refresh()`, `recPoll()`, `cams()`, … explicitly and deterministically (`live_page` keeps the timers for the outage/recovery test), and fails any test whose page threw an uncaught exception or logged a console error. Run it with `~/so101/.venv/bin/python -m pytest tests/ui -q` from the repo root (about 35 s for 45 tests; `-k keyboard` etc. to narrow); Chrome is killed on exit even when tests fail. The one exception to the no-network rule is `test_stage_calib.py`: it opens the page with `Page(cdn=True)`, which lets the three.js / urdf-loader modules load from their CDNs (Chrome runs with SwiftShader so WebGL works under `--disable-gpu`), stubs `/api/calib` (`apidata.calib()` / `calib_none()`) and checks the 3D stage: the 18x12 in mat and its `aruco_<id>` markers at the measured pose, the joint offsets on the URDF robots, the fallback without calibration; it skips when the CDN is unreachable (`SO101_STAGE_SHOT=/path.png` saves a screenshot of the stage). `test_stage_scene.py` reuses that fixture for the mat map (`/api/scene` objects as `obj_<id>` meshes in the mat frame, fade-out, captions) and runs its CAL-chip and SET BACKGROUND button tests on the plain page. `test_stage_wristcam.py` reuses it too, for the WRIST CAM frustum on the follower's `gripper_link` (`apidata.wrist_pose()` as `camera.wrist` in the `/api/calib` payload: position, optical axis, hfov, the fallback without a pose, re-attachment on a `calib` event).
